client_notices.queue(db, appt, settings, now) : if settings.appointment_emails_enabled and appt.client_visible and appt.notify_client, upsert the appointment's pending row (INSERT ... ON CONFLICT on the partial pending index, or select-for-update then update) setting send_after = now + 2 minutes and starts_at/ends_at to the appointment's current times; otherwise do nothing. Call it at the end of scheduling.create_appointment, cancel_appointment, and update_appointment only when starts_at or ends_at changed or client_visible/notify_client turned on (a tech-only reassignment queues nothing). Persist notify_client from the create/update payloads. client_notices.latest_for(db, appointment_ids) -> dict[id, ClientNoticeOut] (pending row if any, else newest row); populate client_notice on every appointment response that scheduling builds (list, get, create, update, cancel).

<task type="auto">
  <name>Task 2: Worker send job</name>
  <files>backend/app/client_notices.py, backend/app/worker.py</files>
  <action>
client_notices.send_due(db, now) -> int: select pending rows with send_after <= now FOR UPDATE SKIP LOCKED (limit 50) under set_org_scope(db, 'all'). For each: load appointment, ticket, settings, last sent notice. If the setting is now off or the appointment is no longer client_visible or notify_client is false: state skipped, reason. Kind: appointment cancelled and a prior sent notice exists -> 'cancelled'; cancelled with none -> skipped 'cancelled before any email'; no prior sent -> 'booked'; times differ from the last sent snapshot -> 'moved'; else skipped 'no client-visible change'. Recipient: ticket contact email else ticket.requester_email; none -> skipped 'no recipient'. Otherwise insert an email_messages row (direction 'out', send_status 'pending', ticket_id, to, subject, body) the same way notices.send_notice does, in the same transaction, mark the notice sent with kind, email_message_id, sent_at and the current snapshot, and audit.record it like notices do. Fixed plain-text templates: subject '[Ticket #N] Appointment booked|moved|cancelled: <subject>'; body with date and time range in the business timezone, the tech's first name, the ticket number and subject, the previous time for moves, and a portal link (settings.public_url + '/portal') only when settings.portal_enabled and the contact has portal_access. Never include appointment notes or cancel_reason. Register send_due in worker.py's run cycle before send_pending so the email goes out in the same cycle, wrapped like the other jobs so one failure does not stop the cycle.

> verification: service postgresql start >/dev/null 2>&1; cd backend && python -m pytest -q tests/test_client_notices.py
  </action>

service postgresql start >/dev/null 2>&1; cd backend && python -m pytest -q tests/test_client_notices.py
