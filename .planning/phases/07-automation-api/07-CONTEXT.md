# Phase 7: Automation & API -- Context

## Phase Goal
Admins define rules that act on ticket and alert events, and external tools (Teams, n8n, scripts) integrate via signed outbound webhooks and permission-scoped API keys.

## Requirements Covered
- REQ-07: rules engine (if X then assign/notify/escalate/create) with audit, outbound webhooks signed and retried from the worker, API keys scoped by permission, hashed at rest and revocable, Teams/n8n delivery via webhooks

## What Already Exists (from prior phases)
- Cookie session auth in app/deps.py (_make_dependency, require(), authenticated()); sha256 token hashing in app/auth/sessions.py; CSRF middleware in app/main.py requires X-Requested-With: psa on unsafe methods
- Permission matrix in app/permissions.py (MATRIX, has_permission); routes declare require(PERM); tests/test_zz_api_contract.py requires summary, tag, permission and a test hit for every route
- ticket_services.create_ticket / update_ticket (single entry for assign/priority/status, also used by bulk_update) / customer_reply / system_note / resolve_by_system; ticket_links.link_related
- notifications.notify (EmailMessage outbox + StaffNotification dedupe, PREFERENCE/HEADLINE maps), notifications.scan_sla and scan_escalations run by worker notify_jobs
- rmm_alerts._create (opens a ticket for an alert) and _clear (Phase 6)
- Worker loop in app/worker.py: plain job functions with dbmod.new_session(), set_org_scope(db, 'all'), Ctx(user=None, scope=Scope.all()); both the idle and mail loops call every job
- crypto.encrypt_credentials / decrypt_credentials (MultiFernet) for secrets at rest; httpx used for outbound HTTP with explicit timeouts; integrations tests use httpx MockTransport fakes
- Staff-internal tables (staff_notifications, ticket_escalations) have no organization_id and no RLS, with explicit grants to psa_app; conftest TABLES truncate list must list every table
- Latest migration 0027 (revision '0027')

## Key Design Decisions
- Tenancy: every new table (api_keys, webhook_endpoints, webhook_deliveries, automation_rules, automation_runs) is staff-internal like staff_notifications/ticket_escalations: no organization_id, no RLS, explicit GRANT SELECT, INSERT, UPDATE to psa_app (no DELETE anywhere: keys are revoked, endpoints disabled, rules archived). Portal code must never read them.
- New permissions: apikey:manage and automation:manage, admin only. API keys may never carry user:manage, apikey:manage or portal:manage (a key cannot mint keys or grant access).
- API key format psa_<8-char prefix>_<secrets.token_urlsafe(32)>; only sha256(full token) hex stored (unique), prefix stored for display; secret shown once on create. Key has name, owner user (the creating admin), permissions (non-empty subset of the owner's role permissions minus the forbidden set), expires_at (expires_in_days 1-730, default 365), revoked_at, last_used_at (written at most every 5 minutes).
- Auth path: a request with 'Authorization: Bearer psa_...' authenticates by API key only (any cookie is ignored). Effective permission = route permission in key.permissions AND has_permission(owner.role) AND owner active AND not revoked AND not expired. Invalid/expired/revoked key -> 401 with record_auth_event('auth.api_key_rejected', detail={prefix}); missing scope -> 403 with auth.denied. authenticated() routes (no permission) reject API keys with 403. The CSRF X-Requested-With check is skipped only for requests carrying an 'Authorization: Bearer psa_' header (browsers cannot add it cross-site). Audit rows written during an API-key request carry detail.api_key_id via a contextvar in app/context.py.
- Events: app/events.py emit(ctx, type, ticket, alert=None, changes=None) with types ticket.created, ticket.assigned, ticket.status_changed, ticket.priority_changed, ticket.customer_reply, ticket.sla_breached, rmm_alert.opened, rmm_alert.cleared (plus 'ping' for webhook tests only). Each emit gets a uuid4 event_id. Emission is in the caller's transaction (outbox).
- Webhook payload v1 is facts only: {id, type, occurred_at, data:{ticket:{id, number, subject, status, priority, priority_id, queue_id, organization_id, organization_name, assignee_id, assignee_name, source, asset_id, url}, alert:{id, severity, message, state}|null, changes:{field:[old,new]}}}. Never ticket descriptions or note bodies.
- Webhook endpoints: kind generic (n8n, scripts) or teams (Adaptive Card message body for Teams Workflows incoming webhooks). Secret is server-generated (token_urlsafe(32)), stored encrypted with crypto.encrypt_credentials, shown once on create and on rotate. The URL is write-only after save (it can carry a Teams sig token): views return url_host and a masked url_preview only.
- Signing: headers X-PSA-Event, X-PSA-Delivery (event_id, the idempotency key), X-PSA-Timestamp (unix seconds), X-PSA-Signature: v1=<hex HMAC-SHA256(secret, f'{timestamp}.{raw_body}')>. Documented with a receiver verification snippet and a 5-minute replay window recommendation in docs/WEBHOOKS.md.
- SSRF: URL must be https with a host, no userinfo, no fragment (query allowed, any port). At save and again at every send, resolve the host with socket.getaddrinfo and refuse if any address is private, loopback, link-local, multicast, reserved or unspecified (ipaddress module), unless the env setting WEBHOOK_ALLOW_PRIVATE_HOSTS=true (default false, for a LAN n8n). httpx with follow_redirects=False, timeout 10s; a 3xx is a failure. Residual DNS-rebinding window between check and connect is accepted and documented.
- Delivery: webhook_deliveries row per (endpoint, event) with unique (endpoint_id, event_id); worker webhook_jobs sends up to 50 due rows per cycle, each committed on its own; 2xx = delivered; otherwise retry after 1m, 5m, 30m, 2h, 6h (6 attempts total) then status failed. Store status code and a 300-char error, never the response body. Endpoint keeps consecutive_failures and last_success_at. Manual retry resets a delivery to pending.
- Rules: automation_rules(name, enabled, trigger event type, conditions jsonb list ANDed, actions jsonb list, position, archived_at, disabled_reason, fire_count, last_fired_at). Condition fields organization_id, queue_id, category_id, priority_id, ticket_type_id, status, source, assignee_id, subject, alert_severity; ops eq, ne, in, not_in, contains (subject only, case-insensitive), is_empty, is_not_empty; validated on save (409 on bad input). All matching rules run in position, id order.
- Rule actions: assign {user_id} (active staff user), set_queue {queue_id}, set_priority {priority_id}, escalate {} (one step more urgent = next lower rank; no-op at the top; system note 'Escalated by rule <name>'), notify {user_id} (notifications.notify with new event rule_notify, preference notify_assigned, dedupe key rule:<rule_id>:<event_id>), webhook {endpoint_id} (enqueue to that endpoint even if not subscribed), create_ticket {subject, queue_id?, priority_id?} (new ticket in the same org, source 'rule', linked related to the triggering ticket).
- Rules run synchronously inside the emitting transaction; each action runs in a savepoint and a failure is recorded in the run trace, never failing the user's request. Loop guard: actions run with an automation depth contextvar set, and emit() only evaluates rules at depth 0 (actions still enqueue webhooks). Idempotency: automation_runs unique (rule_id, event_id). Rate cap: a rule that fired 200 times in the last hour is disabled with disabled_reason and an audit row.
- Dry run: POST /api/automation/rules/test evaluates a saved rule_id or an unsaved rule body against a ticket_id and returns per-condition actual/matched and the actions that would run, changing nothing. GET /api/automation/rules/{id}/runs shows the execution trace.
- SLA breach event: new column tickets.sla_breached_event_at; notifications.scan_sla emits ticket.sla_breached once per ticket when it first sees breached and the column is null (independent of escalation settings).
- Migration 0028 adds the five tables, tickets.sla_breached_event_at and 'rule' to ck_tickets_source; downgrade restores 0027.
- Frontend: new pages ApiKeys (/api-keys, apikey:manage), Webhooks (/webhooks, automation:manage) and Automation (/automation, automation:manage), linked from the App.tsx nav, guarded with can(me, ...).
- Agents: the roadmap's recommended agents were used (backend architect, security engineer); the registry's top matches for these tasks were design personas with low task scores.
- Board quick-assess concerns adopted as constraints: dry-run mode and execution trace, chain-depth limit, per-rule rate cap, idempotency keys, SSRF guard, timestamped HMAC, outbox table, secret rotation, delivery-log tests.
- PRF-001: no owner manual testing until Phase 14; plan 07-04 appends the Phase 7 section to .planning/VERIFY.md and writes docs/verify/automation-api.md.

## Plan Structure
- **Plan 07-01 (Wave 1)**: Automation & API schema, models and permissions -- Add migration 0028, the five staff-internal tables and their models, the tickets.sla_breached_event_at column, the 'rule' ticket source and the apikey:manage / automation:manage permissions, with grant and constraint tests.
- **Plan 07-02 (Wave 2)**: API keys: hashed, scoped, revocable bearer auth -- Let admins create, list and revoke permission-scoped API keys, and authenticate 'Authorization: Bearer psa_...' requests through the existing require() dependency, with audit attribution and an admin page.
- **Plan 07-03 (Wave 3)**: Events and signed outbound webhooks (generic, Teams, n8n) -- Emit ticket and alert events from the services into a webhook outbox, deliver them signed with retries from the worker behind an SSRF guard, support Teams cards and generic n8n JSON, and give admins a webhooks page with the delivery log.
- **Plan 07-04 (Wave 4)**: Rules engine with dry run, trace and loop guard -- Admins define if-this-then-that rules on ticket and alert events that assign, set queue/priority, escalate, notify, call a webhook or create a ticket, with validation, a dry-run tester, a per-run trace, a loop guard, a rate cap, audit, a rule builder page and the Phase 7 verify checklist.
