## Key Design Decisions
- OWNER-APPROVED MONEY RULES (2026-10-21, PRF-002): (1) Fixed-fee projects bill 100% of the fee up front as one invoice line once the project is approved; extra time is never billed. (2) T&M projects bill time at the existing rates and rounding, and the total billed is capped at the project budget; time over the cap is written off at our cost. (3) Tax and deposits are the same as normal invoices.
- Assumed from the owner's answers (stated to the owner, not yet confirmed): milestones (project phases) track progress only and are never billed; project time never draws down block hours.
- Billing modes are exactly 'fixed_fee' and 'tm'. fixed_fee requires fixed_fee_cents > 0; tm requires budget_cents > 0 (the cap). Mode, fee and taxable cannot change after approval (409); a T&M budget may change after approval (audited) and the cap uses the current value, never going below zero remaining.
- Up front means: the fee line is added to the next monthly billing run after approval, or immediately with POST /api/projects/{id}/bill-fixed-fee, which creates a draft one-off invoice holding only that line. A fee is billed once: projects.fixed_fee_invoice_line_id is set, and voiding that line or invoice clears it (via _release) so it can be billed again. Fee line: kind 'project', quantity 1, unit price fixed_fee_cents, tax org.tax_rate_bp if project.taxable (default false, like agreements), description 'Project: <name> (fixed fee)'.
- Project time: tickets.project_id links a ticket to a project of the same organization. _pull_time and _pull_block skip every time entry whose ticket has a project_id; a new _pull_projects in the monthly run handles them. Time on a draft or cancelled-before-approval project stays unbilled. Expenses and product charges on project tickets bill normally and do not count toward the cap.
- Fixed-fee project time in the run: entries through the run end are linked to one $0 line per project, kind 'project', quantity = hours, unit price 0, tax 0, description 'Project: <name>: <h> h covered by the fixed fee' (marks them billed so they never bill twice).
- T&M cap algorithm (pre-tax cents): billed_so_far = sum(amount_cents) of non-voided lines with project_id = p on non-voided invoices; remaining = max(0, budget_cents - billed_so_far). Group the project's unbilled entries by (ticket number, work type id) in that order, price each group exactly as _pull_time does. If amount <= remaining: bill it as a normal 'time' line with project_id set and subtract. If 0 < remaining < amount: bill one line kind 'time', quantity 1, unit price = remaining, same tax rate as the group, description '<normal label> (capped at the project budget)', remaining = 0. Otherwise the group's entries join one $0 line per project, kind 'project', quantity = hours, unit price 0, description 'Project: <name>: <h> h over budget, not billed'. All entries are linked to the line they landed on. A work type with no rate leaves its entries unbilled with the existing warning.
- Worked example to test with exact cents (Remote 150.00/h untaxed): budget 1000.00; run 1: 4 h -> 600.00, remaining 400.00; run 2: two tickets 2 h each -> 300.00 then capped line 100.00, remaining 0; run 3: 3 h -> $0 over-budget line; total billed 1000.00 exactly.
- Schema: projects, project_phases, project_tasks, project_task_dependencies are client-scoped (organization_id, ENABLE + FORCE RLS org_scope, composite FKs to (id, organization_id)), grants SELECT, INSERT, UPDATE; DELETE also on project_phases and project_task_dependencies. Each project task owns exactly one ticket (project_tasks.ticket_id unique; created with source 'project' and project_id set), so time, assignment, dispatch and scheduling come for free. invoice_lines gains project_id (nullable FK) and kind 'project'.
- Dependencies: a task may depend on other tasks of the same project; cycles are rejected (409) by a DFS check; a task with an unresolved dependency shows blocked=true; dependencies never prevent a status change.
- Permissions: new project:write (admin, tech) to create/edit projects, phases, tasks and dependencies; reading needs ticket:read; setting billing fields, approving and bill-fixed-fee need billing:write (admin, billing). A tech can create a draft project without billing fields.
- Project status: draft -> active (approve, needs valid billing fields) -> on_hold <-> active -> completed; draft or active -> cancelled. Budget vs actual: estimate_minutes (sum of task estimates), actual minutes and cost at rates from time on project tickets, billed_cents, remaining cap (T&M) or fee (fixed).
