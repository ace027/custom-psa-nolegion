So `actual_minutes` and `billable_minutes` are the same number, and both ignore non-billable work. The query also does not subtract `block_minutes_covered`.
- `backend/app/projects.py` [minor, 60%]: `add_dependency` checks for a cycle by reading all edges and then inserts, with no lock on the project row or the tasks. Two concurrent requests, A→B and B→A, can both pass `_reaches` and both commit.
- `backend/app/projects.py` [minor, 55%]: `add_phase`, `add_task` and `attach_ticket` use `_open_project`, which rejects completed and cancelled projects. `update_phase`, `delete_phase`, `update_task`, `add_dependency`, `remove_dependency` and `detach_ticket` use plain `get_project`, or skip the project check, so they still work on closed projects.

The move is a select with no drag-and-drop and no success feedback, and the card does not show a pending state.
- `frontend/src/pages/ProjectDetail.tsx` [minor, 55%]: The Taxable checkbox is aligned with `items-end` instead of sitting in a labelled field, and the Fixed fee and Budget inputs omit `inputMode="decimal"`. The tab content is not keyed by project id, so `TaskForm` and `PhaseActions` keep `useState` initial values from the first render. `PhaseActions` seeds `name` and `due` from props and never resyncs them. After the project refetches following another user's edit, the edit form shows stale values.

If a dependency call fails (for example a cycle rejected by the server), the task is already saved. `onDone` does not fire, so the form stays open and the project query is not refreshed. The task shown by the form is then stale. For a new task, a retry creates a duplicate task.
