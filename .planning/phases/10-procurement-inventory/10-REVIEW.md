## Deferred (Medium Confidence)
- `backend/app/procurement.py` [minor, 60%]: `deliver` checks that the organization exists in scope. It does not reject an archived organization. `create_po` and `update_po` do this through `_visible_org`, which raises "That client is archived".
- `backend/app/procurement.py` [major, 65%]: `create_asset` copies the inventory serial (up to 120 characters, `inventory_items.serial_number String(120)`) into `Asset.serial` and `serial_norm`. Those columns are `String(100)` (migration 0010). That `ctx.db.flush()` is not wrapped in `_flush`, so a 101-120 character serial raises a DB `DataError` and the endpoint returns 500, not a 409. The `ReceiveIn` validator and the migration both allow 120.
- `backend/app/procurement.py` [major, 70%]: `deliver()` is about 110 lines and does five jobs: validation, row splitting, asset creation, charge pricing, and audit. The markup and tax resolution has two parallel branches, one for a PO line and one for no line. They go through `resolve_markup` or `_resolve`, and `line.taxable` or `product.taxable`.
- `backend/app/routers/procurement.py` [minor, 60%]: `update_line` calls `ctx.db.expire_all()` before re-reading the PO. `add_line` and `delete_line` have no such call. `_po_out` is also built from ORM objects after the service call. The router works around stale session state instead of the service returning a fresh PO.
- `backend/app/procurement.py` [minor, 50%]: `_po_org` does two `db.get` calls to find the PO's organization. `undo_delivery` uses it to restore the reservation. `get_item` has no eager-loaded relationship to the line and PO.
- `backend/app/routers/procurement.py (with backend/app/procurement.py)` [major, 60%]: `list_inventory`, `get_item`, `list_pos` and `get_po` ignore `ctx.scope`. Only `deliver`, `list_org_inventory` and `_visible_org` call `repo.get_organization(ctx.db, ctx.scope, ...)`. A user with `PROCUREMENT_READ` but a restricted org scope can still read inventory and POs for any client. They can also pass an `organization_id` filter for a client they cannot see.
- `backend/app/procurement_schemas.py (consumed in backend/app/routers/procurement.py)` [major, 65%]: `DeliverIn.quantity` defaults to 1. The router always passes `body.quantity`, so the service's `quantity=None` meaning "the whole row" is never reached. A client that omits `quantity` for a non-serialised row of 10 delivers and bills 1 unit. The rest is split off as a new in-stock row.
- `backend/alembic/versions/0031_procurement.py` [minor, 70%]: Several foreign-key and filter columns have no index: `purchase_orders.organization_id`, `inventory_items.purchase_order_line_id`, `inventory_items.product_id`, `inventory_items.asset_id`, `purchase_order_lines.product_id`. `list_pos` filters by organization, `list_inventory` filters by product, and the po_line FK is used when receiving and deleting.
- `backend/alembic/versions/0031_procurement.py` [minor, 55%]: There is no DB constraint tying inventory state to its charge or asset. For example, `product_charge_id` or `asset_id` can be set while `status='in_stock'`. A delivered item's `asset_id` is not checked against its `organization_id`. Both rules are enforced only in the service layer.
- `backend/app/routers/procurement.py` [advisory, 60%]: The list endpoints (POs, inventory, vendors) have no pagination or limit. `list_pos` and `list_inventory` return all rows ordered by id desc.
- `frontend/src/pages/procurement/Inventory.tsx` [minor, 60%]: The Client cell renders `<Link>{i.organization_name}</Link>`. If `organization_name` is null while `organization_id` is set (the code at line 59 already guards for a null name), the link has no accessible name.
- `frontend/src/pages/procurement/PurchaseOrderPage.tsx` [minor, 70%]: Destructive actions are handled inconsistently. Inventory uses an inline alertdialog for Undo and Consume. Cancel order and Delete rule use blocking `window.confirm`. "Remove" line on a draft PO has no confirmation at all.
- `frontend/src/pages/procurement/PurchaseOrders.tsx` [minor, 60%]: Each line is a six-column grid of eight or more controls. Labels carry repeated "Line N" prefixes and are visible on every row. The `sm:grid-cols-6` layout has no intermediate breakpoint, and the two checkboxes and Remove button sit in separate, unaligned cells. Form errors from `setBad` are not linked to the offending input (no `aria-invalid` or `aria-describedby`).
- `backend/app/routers/procurement.py` [minor, 70%]: `_po_out` takes a `ctx` parameter it never uses. `update_line` calls `ctx.db.expire_all()` to work around stale relationship state. The service also does `ctx.db.expire(po, ["vendor"])` after `refresh`. These are cache workarounds rather than a fix of the underlying staleness.
- `backend/app/procurement.py` [minor, 50%]: `update_line` applies every key from the patch with `setattr`. It ignores nulls only for fields in `LINE_NOT_NULL`. A `product_id` change does not re-default description, cost or taxable. `markup_bp: null` clears the override, which is intended. Unlike `_build_line`, nothing here requires a non-blank description.
- `backend/tests/test_procurement.py` [minor, 65%]: The delivery tests always pass an explicit `quantity`, so the omitted-quantity path (Finding 1) is untested. There is also no test for delivery to an archived client, for an undo after a split delivery, or for the `PROCUREMENT_WRITE` split (billing role can write, tech cannot change markup rules).
- `frontend/src/pages/procurement/MarkupRules.tsx` [minor, 70%]: The rule table is not wrapped in `overflow-x-auto`, unlike every other procurement table. The input and button group in the Actions column can overflow narrow screens.
- `frontend/src/pages/procurement/PurchaseOrders.tsx` [minor, 60%]: Each line row uses `sm:grid-cols-6` with about 9 controls. From 640px to about 800px each column is roughly 90px wide, which crowds the labels "Line N unit cost ($)" and "Line N markup (%)". The two checkboxes and Remove are also squeezed into single cells.
- `frontend/src/pages/procurement/PurchaseOrderPage.tsx` [minor, 75%]: `ReceiveDialog` hand-rolls its own card (`rounded-xl border border-blue-300 bg-surface p-5 shadow-card`) and h2 instead of using `Card`, as `DeliverDialog` does. The same red error `<p>` is copy-pasted in Inventory.tsx (167), PurchaseOrderPage.tsx (141), PurchaseOrders.tsx (214), and MarkupRules.tsx (66, 125, 174) instead of using a shared component.
- `frontend/src/pages/procurement/PurchaseOrders.tsx` [minor, 70%]: "Create purchase order" is silently disabled until a vendor is chosen. The "Add a vendor first (Vendors tab)" hint is plain text with no link or switch action. It sits inside the Orders tab, so the Vendors tab is not reachable from it. Validation is shown only after submit, as a single message for the first error.
- `backend/app/billing.py (void_charge), /home/user/custom-psa-nolegion/backend/app/procurement.py` [major, 70%]: A charge created by delivery is an ordinary `ProductCharge`. `POST /charges/{id}/void` (void_charge) voids it without knowing an `InventoryItem.product_charge_id` points at it. The item then stays `delivered` with a voided charge and `markup_bp` set. It is never billed, and the client inventory card still shows it as delivered. The only repair is to run undo-delivery by hand, and no test covers this path.
- `backend/app/procurement.py` [major, 70%]: A purchase order in `partial` status cannot move anywhere except `received`, and that needs every line fully received. `cancel` accepts only `draft` and `ordered`, and refuses any order with goods received. A vendor that back-orders or never ships the rest leaves the PO in `partial` forever. There is no "close short" or "cancel remainder" transition.
