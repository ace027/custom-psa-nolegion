## Key Design Decisions
- Owner (2026-10-30): run as its own phase before the knowledge base
- Owner: ticket sources manual, email, portal, rmm, api, rule; existing 'ui' becomes 'manual'; tickets created through an API key get 'api'
- Owner: every route under /api/v1 with no /api alias (pre-release, no external consumers); owner updates the Entra redirect URI (VERIFY.md item)
- Owner: automation time is never billable or invoiced; reports show automation minutes as their own column, excluded from utilisation % and from profitability labour cost
- UUIDs are an extra `uuid` column (gen_random_uuid(), core in PG16) on organizations, sites, contacts: NOT NULL, unique, returned in every response; integer ids and routes are unchanged
- assets get source (manual/rmm/import) + external_id unique per (source, external_id) where external_id is not null; no configuration_items table. Backfill: assets with an asset_sources row from a NinjaOne integration -> rmm, from another integration kind -> import, else manual; external_id stays NULL (vendor ids stay in asset_sources; external_id is reserved for the future RMM connector)
- ticket_notes.author_type human/system/ai; backfill system where author_user_id and author_email are both NULL, else human; system_note writes system; ai is reserved
- time_entries.entry_type labour/automation with a CHECK that automation rows are billable = false and invoice_line_id IS NULL; billing and block drawdown also filter entry_type = 'labour' explicitly
- users.entra_tenant_id (String 64, nullable) stored from the verified token's tid at every successful Entra login; read-only in the API
- Enums are Literal types in the Pydantic output schemas so they appear as enums in OpenAPI
- OpenAPI spec committed at docs/api/openapi.json, generated by python -m app.openapi_export (sorted keys, indent 2, trailing newline, no environment-dependent values); a test fails when it is stale
- Board quick-assess constraints: one named test per success criterion; seeded upgrade/downgrade/upgrade rehearsal asserting row counts, uuid uniqueness and the restored ui source; a test that no route is served outside /api/v1 (health probes excepted); a billing + report test proving automation entries are never invoiced, never in utilisation % and never in labour cost; docs/API.md with the /v1 versioning policy
- PIT-001: every schema plan runs test_isolation.py and test_backup_restore.py
- Out of scope: webhook intake, RMM connector, NinjaOne inbound adapter, monorepo, Client 360, unified search, AI assistant. Project budget-vs-actual is unchanged

## Plan Structure
- **Plan 12-01 (Wave 1)**: Integration-readiness schema, models, schemas and writers -- Migration 0033 adds UUIDs, rmm_client_id, asset source/external_id, ticket source values and external_ref, note author_type, time entry_type and users.entra_tenant_id, with backfills; models, output schemas and every writer use them.
- **Plan 12-02 (Wave 2)**: Automation time kept out of billing; reported separately -- Billing runs, block drawdown and project T&M billing select labour time only, and utilisation and profitability report automation minutes in their own column, outside utilisation % and labour cost.
- **Plan 12-03 (Wave 2)**: Frontend: branding config, client scope module, note authors and new fields -- Product name, mark, logo and colours come from one branding config; every client-scoped API path and client link goes through one clientScope module with a useClientScope hook; system and AI notes are styled distinctly and filterable; the frontend types carry the new fields.
- **Plan 12-04 (Wave 3)**: /api/v1 everywhere and the committed OpenAPI spec -- Every route is served under /api/v1 (health probes excepted), the frontend, tests, docs and OIDC redirect follow, and the OpenAPI spec is exported to docs/api/openapi.json with a test that fails when it is stale.
