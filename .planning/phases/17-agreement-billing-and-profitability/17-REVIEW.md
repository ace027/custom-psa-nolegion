## Deferred (Medium Confidence)
- `backend/app/ticket_services.py` [major, 70%]: `_check_agreement` checks only that the agreement belongs to the client. It does not check that the agreement is in force on the entry's `work_date`. `add_time` also copies `ticket.agreement_id` without any date check. Example: an all-inclusive flat agreement ends 2026-10-31, and a ticket opened in October keeps it. Time logged on 2026-11-05 inherits the agreement and `_not_all_inclusive()` excludes it from invoicing. The post-expiry work is never billed. Backdated time attached to an agreement that starts later is lost the same way.
- `backend/app/report_metrics.py` [minor, 75%]: `_check_group` checks `group` against `("client", "agreement")`, but the router already types `group` as `metrics.ProfitGroup`, a `Literal` of those two values. FastAPI rejects any other value with a 422 before `utilisation` or `profitability` runs. The `Conflict` branch cannot be reached from any route. `csv_for` is also used by the scheduled emails, which pass fixed values.
- `backend/app/report_metrics.py` [minor, 60%]: When `group` is `"client"`, `profitability` builds the row identity dict inline. It repeats the keys of `_agreement_fields` and fills `agreement_id`, `agreement_name` and `agreement_type` with `None`. `_agreement_fields` is the same helper that builds this dict in agreement mode. Any new identity field must now be added in two places.
- `frontend/src/pages/billing/Agreements.tsx` [major, 60%]: The inline editors have no visible labels. The all-inclusive checkbox sits in a label, but the rollover select, cap input, hours input and quantity input rely only on `aria-label` or a placeholder ("cap h", "why?"). The "h" unit after the hours input is bare text. These inline controls don't use the `Field` component or the `inputCls` token that the form uses. The cap input takes hours, but the unit is not visible.
- `frontend/src/pages/TicketDetail.tsx` [minor, 60%]: The new Agreement column puts a full-width `inputCls` select into a 7-column table in the Time card. The header row has no `scope="col"` on its cells. The read-only fallback prints "Agreement #id" for any user without `billing:read`, because the agreements query is disabled for them.
- `backend/app/reports.py (outside the listed files; the gap comes from the _not_all_inclusive() filter added in backend/app/billing_repo.py)` [major, 70%]: `_not_all_inclusive()` was added to `unbilled_time` and `orgs_with_billables` only. The unbilled/WIP report query in `reports.py` (labour, billable, `invoice_line_id IS NULL`, `minutes_billable > 0`) was not given the same filter. Time attached to an all-inclusive flat agreement will still show as unbilled revenue there.
- `backend/app/schemas.py` [advisory, 55%]: Mid-file `from app.report_schemas import ...  # noqa: E402` imports, plus the `ReportRangeOut` alias, are appended at the bottom of `schemas.py`. The phase-17 report models sit away from `report_schemas.py`, where `ProfitabilityRowOut` and `UtilisationReportOut` are defined.
- `backend/app/ticket_services.py` [advisory, 50%]: The rule that a ticket or time entry may only use an agreement of its own client is enforced in `_check_agreement` only. The DB foreign key is a plain `agreements.id` reference, with no composite `(agreement_id, organization_id)` check. Other paths that write `agreement_id` would bypass the rule. Today only create/update ticket and add/update time write it, and those all call the check.
- `frontend/src/pages/billing/Agreements.tsx` [minor, 60%]: The table is not responsive. It has no `overflow-x-auto` wrapper and no min-width. The Type cell now holds a select, a cap input and a Save button inline, and the Qty cell holds an input, a reason input and a Save button. The form uses `sm:grid-cols-4` with a bare `grid` below `sm`, so fields have no explicit single-column mobile layout.
- `frontend/src/pages/billing/Agreements.tsx` [minor, 65%]: The rollover cap Save button shows when `Math.round(Number(capText)*60) !== (a.rollover_cap_minutes ?? 0)`. Clearing a cap that is set gives 0 versus the stored minutes, so the button shows. Setting a cap of 0 against a stored null gives 0 versus 0, so the button is hidden. A cap of 0 hours is a different value from "no cap" (null), and `capText ? ... : null` treats "0" as 0 minutes. The user can't save "0" when no cap is stored, and the UI doesn't say what an empty cap means.
- `frontend/src/pages/reports/ProfitabilityReport.tsx` [minor, 65%]: The group radios are a `div role="group"` with no visible legend, and radios in a group should use a `fieldset` and `legend`. Their labels use no shared token or component, which differs from the other controls. The `agreement_type` is rendered as a raw enum ("flat", "per_user") while the Agreements page maps it to labels ("Flat fee"). The empty-state `colSpan={12}` is wrong, because the table has 10 columns in client mode and 12 in agreement mode. The flat-fee, all-inclusive and block distinction is not visible in the report. Rows with a null agreement show "No agreement" but no row identifier.
- `frontend/src/pages/TicketDetail.tsx` [minor, 55%]: The ticket Agreement select is shown only when `canWrite && ag.all.length > 0`. If the client has no agreement, or the user lacks `billing:read`, it falls back to a read-only "No agreement" label with no explanation. A user without `billing:read` sees "Agreement #N" instead of a name. The ticket-level select has no empty or loading state while the query is in flight. The `sel` helper's `Number(e.target.value)` is also applied to agreement IDs. The time-entry select includes an option filter by `work_date`, but if the entry's agreement is excluded from `ag.all` (different org) its value matches no option. The ticket select and the time-entry select have different labelling: the ticket one is visible through `Field`, the entry one is `aria-label` only. Changing the ticket's agreement doesn't tell staff whether existing time entries move with it. The time-entry select also has no pending state.
- `backend/app/billing_repo.py` [minor, 60%]: `_not_all_inclusive()` is applied to `unbilled_time` and to the billing-run organisation query. The `/reports/unbilled` aggregate in `reports.unbilled` does not apply it. Billable time attached to an all-inclusive flat agreement therefore still appears there as unbilled revenue. It is priced at the hourly rate and never invoiced. I read the code and did not run it, so this is inferred.
- `frontend/src/pages/TicketDetail.tsx` [minor, 50%]: `useAgreementOptions` is enabled only when the user has `billing:read`. For a technician with ticket and time write permission but no billing read, the agreement selector never renders. The ticket and time-entry agreements show read-only as "Agreement #id". The backend allows the change, because `PATCH /tickets` and `PATCH /time-entries` check only ticket and time permissions. The hook also fetches every agreement for all organisations and filters them client-side.
- `backend/app/ticket_services.py` [major, 70%]: `add_time` copies `ticket.agreement_id` without checking that the agreement covers the entry's `work_date`. `_check_agreement` checks only the organization. The ticket's agreement is set once, at create or triage. Time logged after an all-inclusive flat agreement has ended, or backdated to before it started, still attaches to that agreement. `_not_all_inclusive()` in `billing_repo.py` filters on `agreement_id` alone, so that time is never billed. The same happens when a client renews onto a new agreement and old tickets keep pointing at the expired one.
- `backend/app/report_metrics.py` [minor, 55%]: Block draw-down also consumes time with `agreement_id` NULL. A line carrying `agreement_id` takes its revenue from the block, and `labour` is keyed by the time entry's own `agreement_id`. Unattached time that the block covered therefore puts its revenue on the block row and its labour cost on "No agreement". The block's margin is overstated and the "No agreement" row is understated.
- `backend/app/report_metrics.py` [minor, 50%]: `billable_minutes` per agreement counts all-inclusive flat time that is flagged billable but never invoiced. `billable_bp` is not shown per agreement.
- `backend/app/billing.py` [minor, 50%]: `rollover` and `rollover_cap_minutes` can be changed at any time, and the carry is recomputed from history. Switching `expire` to `roll`, or raising the cap, retroactively creates carried minutes for months already finalized and billed under `expire`. Nothing blocks or warns about this. The cap is also not required to be a multiple of the billing increment, so carried minutes can end up off-increment.
